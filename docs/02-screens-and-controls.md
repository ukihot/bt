## 3画面(モニタ)

プレイヤーは帳場に座り、店内3箇所の監視カメラのログを同時に眺める。画面は上下2段のグリッド:

```
┌───────────────────────────────┐
│           焼成室 (Kiln)          │  ← 唯一の操作対象
├────────────────┬────────────────┤
│   外 (Outside)  │  売り場 (Floor) │  ← 読むだけ
└────────────────┴────────────────┘
```

3画面は完全に独立して流れ、それぞれ自分の速度でログを生成する(`Pane::spawn_interval_secs`,
`src/domain/pane.rs:62`)。カーソル窓の行数(`capacity`)は焼成室を基準に黄金比φで外・売り場を
導出しており(8:5)、画面上の縦の面積比もこれに揃えてある(`Pane::capacity`, `pane.rs:52`)。

| 画面 | 書き手の立場 | 役割 |
|---|---|---|
| 焼成室 | 職人の作業記録 | **唯一の操作対象**。プレイヤーが実際に判断し対処する |
| 売り場 | 接客係の応対記録 | **ルール変更の発信源**([04-rules-and-rumors.md](04-rules-and-rumors.md)) |
| 外 | 警備の定点観測記録 | **脅威との距離を示すステータス表示**(体温計) |

仕様上、外・売り場に操作対象は存在せず、画面を切り替えるという概念自体がない
(`CLAUDE.md` §3.1)。プレイヤーの注意は「操作している焼成室」と「操作できないが目を離せない
外・売り場」の間で常に引き裂かれる — これが「抽象タワーディフェンス」の実体。

## プレイヤーの動詞

`Verb`(`src/domain/verb.rs`)は2つだけ:

- **削除(Z)** — 見た目は罰マークではなく `═` で左から順に上書きしていくワイプアニメーション
  (`src/screens/playing/render.rs` の `wipe()`)
- **検印(X)** — `✓` スタンプ

カーソル移動は `J`(下)/`K`(上)。静観は動詞ではなく、カーソルの届く範囲を何も押さずに
通過させることそのものが静観になる。

## 判定の遅延(このゲームの核となる時間差)

**押した瞬間には何も起きない。** 削除・検印は対象行に「印をつける」だけの操作で、実際の判定
(正しかったか、間違っていたか)は、その行がカーソルの届く範囲(`Pending` のウィンドウ)から
外れる瞬間に確定する(`src/screens/playing/pending.rs`)。

実装:

1. `Pending::push` が新しい行を末尾に追加し、`capacity` を超えた分を前方から evict する
   (`pending.rs:51`)
2. evict された行は `PendingLine.mark`(押した時点で付いていた印、無ければ `None`)を持ったまま
   `domain::resolve()` に渡され、そこで初めて `Outcome { corruption, income, zone_bump }` が
   確定する(`src/screens/playing/spawn.rs:149-170`)
3. カーソルは既定で最新行に追従(`following`)するが、`J`/`K` で手動移動すると追従が外れる

印をつけた直後の安心感と、後から効いてくる結果のズレがこの作品の時間差の恐怖。外・売り場を
眺めている間も焼成室のログは流れ続け、カーソルの届く範囲を勝手に通過して確定していく —
見ていなかった行は静観したのと同じ結果になる。

## 反応の三分類 — 分類ごとに正解はちょうど1つ、それ以外はタタリ

`Classification`(`src/domain/log_line.rs`)。2026-07-20 のリファクタで、分類ごとの正解の動詞を
`Classification::correct_action()` が返す純粋関数として定義し直した:

| 分類 | 正解 | 正解を外した場合(`resolve()` の帰結、分類問わず一律) |
|---|---|---|
| `Normal`(通常業務行) | 検印 | corruption +2・income -1・**zone_bump** |
| `ShouldReact`(反応すべき行) | 削除 | corruption +4・income -1・**zone_bump** |
| `ShouldNotReact`(反応してはいけない行) | 静観(`None`) | corruption +6・income -2・**zone_bump** |

正解を引き当てた場合のみ `zone_bump: false` の"安全"な結果になる(`ShouldReact` の正解は
`corruption -1.0 - relief` で実際に corruption を削り、他2分類の正解は corruption/income を
動かさない)。**「正解以外はすべてタタリ」がこのゲームの唯一のルール** — かつては「反応すべき
行を見逃しても corruption だけ、一部の禁忌由来の行だけ `zone_bump` も立つ」という `taboo` フラグ
による非対称な例外があったが、2026-07-20 に廃止した(`LogLine.taboo`/`Effect::Enable`の`taboo`
引数/`Verdict::Active`の`taboo`ペイロードはすべて削除済み)。**通常業務行を検印し忘れる/誤って
削除することも、もう「安全な誤操作」ではない** — 大半を占める通常業務行に能動的な検印を要求する
ことで、旗揚げゲーム(赤旗が上がったら白旗を上げるか否かの判断遊び)の「既定の動作と、そこからの
例外的な静止」という緊張構造をこのゲーム全体に敷いている。

どの行がどの分類に属すかは固定ではない。売り場発のルール変更([04-rules-and-rumors.md](04-rules-and-rumors.md))
によって、それまで「反応すべき」だった書き方が「反応してはいけない」に反転する、あるいは
その逆が起こる。ルールが変えるのは分類そのものであって、分類ごとの正解・タタリの対応表
(上の3行)自体は変わらない。脅威・異常ごとに「今どの分類に属しているか」を突き合わせた一覧は
[04-rules-and-rumors.md の正解アクション定義表](04-rules-and-rumors.md#正解アクション定義表)を参照。

### `relief` — 援助系の禁忌によるボーナス回復

一部の禁忌は「正しく対処すると通常より深く救われる」援助系(`Effect::Relieve`)で、
`LogLine.relief` に正の値が乗る。これは正しく対処できた場合の corruption 回復量を追加で
増やすだけで、`zone_bump` には一切影響しない — 脅威の物理的な距離(`Zone`)そのものは、
援助系の禁忌であっても一切動かない(原則2: 距離だけが縮む)。
